## 0. Why we are here (the diagnosis, settled)

Three supervised fine-tuning runs, three regressions on the target skill (CanItEdit,
descriptive, n=52, matched, 2560-token whole-file, failure-classified):

| run | recipe | vs donor 53.85% |
|---|---|---|
| C5 @2167 | 70% reasoning / 30% edit-diff | −11.5 |
| C5 @3044 | 65% edit-diff / 35% reasoning | −17.3 |
| donor + thinking mode | zero-train "free win" attempt | −13.5 |

Root causes, in order of depth:
1. **Surface:** output-format mismatch — we trained diff output (hashline, unified
   patches) for a whole-file task (fixed in commit 2633361; EditPackFT whole-file).
2. **Structural:** **Qwen3.5-4B is a Feb-2026 frontier post-trained model, and every
   open dataset we can feed it is at or below its own output quality.** SFT is
   imitation; imitating data weaker than yourself makes you worse. Proof: EditCoder
   (the CanItEdit authors' own EditPackFT recipe) tops out in the low-40s on
   DeepSeek-6.7B-base — *below* our donor's 53.85% zero-shot. The published small-model
   edit-training literature produces models weaker than our starting point.
3. **Consequence:** at $0, exactly two teachers are smarter than the donor — a much
   bigger open model (32B+, quota-bound, slow) and **the execution sandbox** (grades
   ground truth, runs local, free forever). The sandbox is the only scalable one.

This is corroborated by 2025-2026 theory:
- **RL's Razor** (arXiv 2509.04259): on-policy RL forgets less than SFT because it is
  implicitly KL-minimal; SFT can drift arbitrarily far from base. Our regressions are
  this paper's predicted SFT behaviour, verbatim.
- **LoRA Without Regret** (Thinking Machines, 2025): LoRA matches full fine-tuning for
  RL (~1 bit/episode of information → r16 all-linear is ample capacity).

**Killed as an improvement mechanism: naive imitation SFT.** Retained only as an
optional single-night *control arm* (C5E whole-file) to close the chapter with data.

## 1. Identity — what AVA v3 uniquely is

Two pillars, blended into one artifact:

> **The first fully-local coding model that (a) improves itself overnight against an
> execution verifier — gated so it can never regress — and (b) scales its own compute
> per token to the laptop's live power and thermal budget, getting smarter while it
> charges and never wasting a watt.**

- **Pillar A — Self-Improving Local.** The ratchet (§2): generate → verify → prefer
  what passed → gate. Ground-truth signal, monotonic by construction, no cloud.
- **Pillar B — Elastic Power-Adaptive.** Per-token adaptive depth (MoR-style early
  exit) under a battery/thermal governor, so the same model runs full quality on AC
  and a lighter self-extracted path on battery/throttle.

Novelty is **composition of existing techniques on a strong donor**, not a
from-scratch architecture. No known system ships self-improving + power-elastic +
4 GB-local together. The blend is the differentiator: a model that is *usable now*
(donor-grade), *improves while idle/charging*, and *cannot degrade* — the exact
failure mode that has cost us a month becomes structurally impossible.

## 2. The spine — the verified ratchet (LOCKED)

Three layers, all built from parts already in-repo (sandbox, checkpoint fabric,
resumable failure-classified evals, GGUF chain, hw profiles, gate.py).

**Layer 1 — overnight verified loop (weights).** On the A2000, unattended:
model generates *k* edit attempts per task → sandbox executes tests → verified
pass/fail groups → **GRPO on execution reward** (§4) with a LoRA. Reference model
costs zero extra VRAM (adapters-off *is* the reference in PEFT). Candidates are
regenerated each night from the *current accepted* weights → approximately on-policy
(RL's Razor freshness rule). Ground-truth reward cannot teach under-editing,
verbosity, or minimality — the failure modes of every prior run.

**Layer 2 — the gate (never-regress guarantee).** Weekly, automatic: candidate LoRA
runs the eval suite (CanItEdit-52 + HE+/MBPP+ floors, all resumable). **Accept only
if non-regressing on every axis; else discard the week.** `gate.py` already exists.
Improvement becomes monotonic; the "regression discovered after days of compute"
problem becomes mechanically impossible. Satisfies INVENTION.md D8.

**Layer 3 — verifier-in-loop inference (product, shippable immediately).** At answer
time: generate edit → run tests → on failure feed the error back → bounded retry
(k≤5). SWE-agent literature: +10-20pp from execution feedback. Plausibly lifts
53.85% → ~65-70% *effective* editing this week, zero training. Same generate-verify
machinery as Layer 1.

**Task engine (the one genuinely new build) — three escalating tiers of self-reliance:**
- (a) **Donor-written tests over EditPackFT:** donor writes tests for a whole-file
  edit pair; keep iff gold-after passes and before fails → instant executable edit
  corpus. Decontaminate against CanItEdit with the existing 10-gram filter.
- (b) **Mutation:** inject bugs into passing tested code; model must repair; tests
  pre-exist.
- (c) **Self-play (AZR-style):** model proposes task+hidden-tests, solves, verifies —
  the C6 endgame, warm-started by (a)+(b).
- **Personal-repo tier (uniqueness amplifier):** the user's own projects' test suites
  become verifier tasks. AVA specializes to the user's codebase overnight — no
  contamination, maximal relevance, fully private/local. (Ties to test-time
  adaptation, arXiv 2511.04847.)

**Infrastructure (native Windows-first, no Docker required):**
- Generation + interactive: `llama-server`, native CUDA (proven 18 t/s; MTP + slots).
- Nightly trainer: native Python, torch CUDA + bnb 4-bit (a2000 profile: seq 640,
  mb1×ga32). Triton/FLA not required (skipped on Windows; optional WSL2 lane later
  for 1.5-2.5× train speed — A2000 is Ampere/sm86, the GPU supports FLA; Windows
  blocks Triton, not the card).
- Sandbox: Tier 0 = existing subprocess sandbox + **Windows Job Objects** (RAM cap,
  process-count cap, kill-on-close) + a firewall rule blocking the sandbox venv's
  python outbound. Tier 1 = slim WSL2 jail before mutation/self-play scale-up.
- Orchestrator: plain Python + **Windows Task Scheduler** (00:30 start, time-boxed
  like a training shard, locally checkpointed, safe to kill mid-anything).
- Storage: **local-first** `D:\AVA\ratchet\` (task bank, generations, pairs, LoRA
  snapshots). HF Hub receives only the weekly *accepted* snapshot → quota/Xet pain
  leaves the loop.

## 4. Tier B — training-method core (refines the ratchet, not a new direction)

**GRPO on execution reward + LoRA r16 all-linear + PiSSA init.** This is the correct
instantiation of "ORPO on pass/fail," per the 2026 post-training consensus:
SFT (format) → preference (DPO/ORPO) → **RL with verifiable rewards (GRPO/DAPO)**.

- GRPO: generate K per task, score each by tests, advantage = group-normalized,
  critic-free (~25% less memory than PPO). DAPO adds clip + dynamic sampling for
  stability — adopt DAPO's stabilizers if GRPO variance bites.
- LoRA r16 is provably sufficient (LoRA Without Regret: RL needs ~1 bit/episode).
- On-policy freshness (RL's Razor) + weekly KL-to-donor as drift instrumentation.
- Reward-hacking guards (R20, already specced): hidden test halves, mutation
  kill-checks (≥30% mutants must fail), property templates.

Sources: post-training survey (llm-stats 2026), GRPO/DAPO/RLVR line, arXiv 2509.04259,
thinkingmachines.ai/blog/lora.

## 5. Tier C — architecture bolt-ons (GATED: unlock only after the first non-regressing night)

Each rides the spine; none replaces it.

- **Mixture-of-Recursions (MoR)** — arXiv 2507.10524 (NeurIPS 2025). Shared layers
  applied recursively with a per-token router → **adaptive depth + early exit**. This
  is the published, working form of our HRM recurrent-depth note. Delivers Pillar B's
  "per-token elastic compute." Compose as inference-time early-exit first (no
  retrain); learned routing later.
- **Titans: test-time memory** — arXiv 2501.00663 (Google). Neural long-term memory
  module that writes to itself at test time via a gradient "surprise" signal; scales
  to 2M context. Serves "long context" + the self-improving theme as a memory add-on.
- **MatFormer / elastic inference** — arXiv 2310.07707 (Gemma 3n/4). Nested submodels,
  one model → many sizes without extra training. Ideal for the power governor (full
  on AC, lighter submodel on battery). Caveat: true MatFormer bakes submodels at
  *train* time; Qwen3.5 lacks them → the cheap honest version is **MoR early-exit +
  `-ngl` offload**, which captures most of the elastic benefit with no retrain.
- **Multi-LoRA per-token routing (MoLoRA)** — the ChatGPT "7B-total/3B-active hybrid"
  done correctly: one base + several adapters routed per token, hot-swappable. Only
  pays off once the ratchet has produced ≥2 adapters each beating the donor at
  something. Phase-5 composition.

## 7. Power & thermal governor (spec — the "recharge while training" requirement)

Physics: batch-1 LLM **decode is memory-bandwidth-bound**, cores stall on VRAM, so
power caps rarely trigger; **SM clock-locking recovers up to ~32% decode energy at
negligible throughput loss** (arXiv 2605.11999; mobile DVFS arXiv 2507.02135). Lock
SM clocks via `nvidia-smi -lgc` rather than power-capping.

Governor module (~100 LOC): reads `psutil.sensors_battery()` + `pynvml` every 30 s.

| State | Policy |
|---|---|
| On battery | Pause loop entirely. Never train on battery. |
| Plugged but % falling | TRICKLE: deepest clock cap, 1 slot, 50% duty (45 min work / 15 min pause) → brick catches up, **battery recharges mid-run**. |
| Plugged + healthy (≥90%, stable) | BALANCED: GEN at capped clocks (~1050-1200 MHz, ~35-50 W); TRAIN at ~1300 MHz cap or full-clock duty-cycled. |
| GPU ≥ 83 °C | Back off one level. |

CPU: overnight `powercfg` processor-max ~85% (kills i7-11850H 100 W+ boost spikes;
sandbox barely notices). Phases sequential, never concurrent (server down before
trainer up). Overlap CPU test-execution of candidate N with GPU generation of N+1.

**Manual one-time (user only):** BIOS/vendor **battery charge cap ~80%** (a laptop on
nightly loops plugged in 24/7 at 100% degrades its battery); confirm power-brick
wattage (150 W vs 200 W sets BALANCED aggressiveness).

## 8. Roadmap — build order & gates

- **Phase 0 (this doc).** Direction captured. Re-hunting closed.
- **Phase 1 — instrument & baseline.** Power governor + MTP GGUF + ik_llama.cpp bench.
  One measured baseline night (throughput, tokens/night, energy, thermals). *No
  training.* Gate: governor keeps the battery ≥ its start % overnight while plugged.
- **Phase 2 — verifier-in-loop inference + task engine tier (a).** Retry-on-test-fail
  wrapper around GGUF/llama.cpp + sandbox; measure effective CanItEdit @k=3.
  Donor-written-tests corpus over EditPackFT, decontaminated, ~1-2k tasks banked.
  Gate: effective editing > 53.85% at k≤3.
- **Phase 3 — nightly GRPO + weekly gate → first gated win.** GRPO-on-execution,
  LoRA r16, PiSSA init, on-policy freshness. First unattended, gated, battery-safe
  week. **Gate: one accepted (non-regressing) weekly snapshot.** ← *this gate unlocks
  Tier C.*
- **Phase 4 — elastic (Pillar B).** MoR early-exit + governor integration → per-token
  power-adaptive compute. Optional MatFormer-spirit submodel extraction.
- **Phase 5 — memory & composition.** Titans test-time memory (long context) →
  multi-LoRA per-token routing (the real hybrid).
- **Continuous:** personal-repo verifier tier; sleep-time repo indexing (Gigatoken);
  weekly KL-to-donor drift check.

**Optional control arm (skippable):** one overnight C5E whole-file SFT night, purely
to bank the "does format-aligned SFT even hold 53.85%" data point and close the SFT
chapter. Not on the critical path.
